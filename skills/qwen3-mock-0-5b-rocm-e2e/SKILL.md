# Qwen3 Mock 0.5B ROCm E2E

## General Description

This skill captures the standing 0.5B Qwen3 mock validation path for the Relax
ROCm stack. The model is a generated local Qwen3-compatible checkpoint with
533,126,144 random parameters and the real Qwen3 tokenizer, so it validates
infrastructure boundaries, not model quality.

The path is useful because it is large enough to exercise realistic Megatron,
SGLang, W&B, and checkpoint behavior, while being cheaper than the full
Qwen3-4B TP2 run. It supersedes the historical 1M mock checkpoint, which was
too small to be a meaningful standing regression target.

## When to Apply

Use this knowledge when:
- A Relax, Megatron, SGLang, W&B, or checkpoint change needs a quick ROCm e2e
  regression run before the full Qwen3-4B validation.
- The run must prove real rollout, actor training, W&B application metrics, and
  optimizer-inclusive Megatron `torch_dist` checkpointing.
- A four-GPU MI210 smoke or overnight run is needed with actor TP2 and two
  rollout engines.

Do NOT use when:
- The goal is reward quality, answer quality, or learning behavior. The model
  is random, so invalid answers, reward `-1.0`, zero advantages, and
  `train/loss=0.0` are expected.
- The goal is to replace the Qwen3-4B no-offload TP2 validation. This mock path
  is a fast infrastructure regression, not the final production proof.
- A proposed shortcut disables checkpointing, disables optimizer save, or
  uses CPU optimizer offload.

## Recommended Practice

### Step 1: Know What This Run Proves

Treat the 0.5B mock as an infrastructure regression. It proves that the current
ROCm Relax stack can load the HF asset, start SGLang transformers rollout,
initialize Megatron Qwen3Bridge, update weights, execute actor optimizer steps,
report W&B application metrics, and save optimizer-inclusive checkpoints.

Do not interpret answer correctness, reward value, or loss value as model
quality. The checkpoint is random by design.

### Step 2: Run a Short Smoke When Changing the Path

Use the two-GPU smoke for quick validation:

```bash
source /vast/users/qirong.ho/miniforge3/etc/profile.d/conda.sh
conda activate relaxrl_rocm
SAVE_CHECKPOINTS=1 NUM_ROLLOUT=2 SAVE_INTERVAL=1 CKPT_FORMAT=torch_dist NO_SAVE_OPTIM=0 \
  ./amd_qwen3_mock_2gpu_e2e.sh
```

Expected proof:

```text

Actor training completed step 0/2
saving checkpoint at iteration       0 ... in torch_dist format
Actor training completed step 1/2

```

### Step 4: Audit the First Checkpoint Boundary Before Calling It Healthy

For `SAVE_INTERVAL=20`, the first durable production checkpoint is iteration
19. Startup, rollout, step 0, and step 1 are not enough for overnight health.

Audit the latest checkpoint with a metadata check like this:

```bash
python - <<'PY'
from pathlib import Path

save_dir = Path("/path/to/Qwen3-Mock-0.5B_mcore_4gpu-run")
latest = (save_dir / "latest_checkpointed_iteration.txt").read_text().strip()
metadata = save_dir / f"iter_{int(latest):07d}" / ".metadata"
text = metadata.read_text(errors="ignore")
required = [
    "optimizer.state.exp_avg",
    "optimizer.state.exp_avg_sq",
    "optimizer.state.fp32_param",
]
print("latest", latest)
print("optimizer_state", all(key in text for key in required))
print("dataset_state", (save_dir / "dataset" / f"global_dataset_state_dict_{latest}.pt").exists())
PY
```

Healthy output must show a non-empty latest iteration, optimizer state, and
dataset state.

### Step 5: Require W&B Application Metrics

The W&B run is healthy only if it contains application metrics such as:

```text
train/step
train/loss
train/entropy_loss
rollout/step
rollout/raw_reward
perf/step_time
perf/save_model_time
```

System-only W&B charts are not enough. If logs show metrics POSTs but W&B has
only system metrics, debug `MetricsService` run joining and flush behavior
before debugging the model.

## Failure Modes

| What Failed | Why | Lesson Learned |
|-------------|-----|----------------|
| `Qwen3-Mock-1M` became the default target | It was too small and did not match the requested mini-model scale | Use the 533M `Qwen3-Mock-0.5B` asset as the standing mock path |
| A run was considered healthy before checkpointing | `SAVE_INTERVAL=20` means no production checkpoint exists until zero-based iteration 19 | Wait through iteration 19 and audit optimizer and dataset state |
| W&B appeared healthy from system charts only | The system monitor can log without training application metrics being flushed | Require namespaced train/rollout/perf metrics in the primary run |
| Checkpoint shortcuts looked convenient | Disabling checkpointing or optimizer save removes the core validation boundary | Keep `CKPT_FORMAT=torch_dist` and `NO_SAVE_OPTIM=0` |
| Quality metrics looked bad | The model is random, so rewards and loss are not meaningful | Use this path only for infrastructure validation |
